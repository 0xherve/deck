Lesson 1.2

Read the Client Like a User

Forget React terminology for now. This lesson follows what actually happens when you click a file in the sidebar — from the click to the API call to pixels on screen.

The client's structure

The entire client is a tree of components that render inside each other. Here's the nesting:

RootLayout (__root.tsx)
├── AppSidebar (app-sidebar.tsx)
│   ├── Home link
│   ├── Changes link
│   └── FileTree (FileTree.tsx)
├── [Current Route] (Outlet)
│   ├── / → HomePage
│   ├── /v/* → FileViewRoute
│   └── /d/* → DiffViewRoute
└── SourceControlPanel

RootLayout is the shell — it's always on screen. The Outlet is a hole where the current route's component gets rendered. When the URL changes, only the Outlet content swaps.

Trace: clicking a file in the sidebar

Here's exactly what happens when you click "README.md" in the file tree:

Step 1: The click handler

In FileTree.tsx line 134, the file button has an onClick:

onClick={() => navigate({ to: "/v/$", params: { _splat: entry.path } })}

This tells TanStack Router: "change the URL to /v/README.md." That's all the FileTree does — it doesn't load the file, it just navigates.

Step 2: The route matches

In router.tsx, the route /v/$ is registered with component: FileViewRoute. The $ is a "splat" parameter — it captures everything after /v/. So for /v/src/main.tsx, the splat is src/main.tsx.

Step 3: FileViewRoute runs

In routes/v.$.tsx, several things happen at once:

  • It reads the file path from the URL params: params._splat
  • It dispatches OPEN_TAB to add this file to the tab bar
  • Two hooks fire in parallel:
    • useFileContent(filePath) → GET /api/file?path=README.md
    • useFileMeta(filePath) → GET /api/file-meta?path=README.md

Step 4: The right viewer is chosen

Once both hooks have data, FileViewRoute decides what to render:

Is it markdown (.md/.mdx)?  → MarkdownEditor (tiptap)
Is it an image?              → ImageViewer
Is it binary?                → BinaryViewer
Otherwise                    → CodeViewer (read-only, syntax highlighted)

This decision chain is just a series of if statements. There's no plugin system or registry — it's straightforward conditional logic.

How tabs work

Tabs are managed with useReducer — React's built-in state machine. The state shape is simple:

{
  tabs: [{ path: "README.md", dirty: false }, ...],
  activeTab: "README.md"
}

Four actions can happen:

  • OPEN_TAB — adds a tab (or just activates it if already open)
  • CLOSE_TAB — removes a tab and picks a neighbor as active
  • SET_ACTIVE — switches the active tab
  • SET_DIRTY — marks a tab as having unsaved changes

This state lives in __root.tsx and is passed down through TabsContext. Any component can read or update tabs by calling useTabs().

Why useReducer instead of useState? When you have multiple related state values (tabs list + active tab) and actions that need to update them together (closing the active tab must also pick a new one), a reducer keeps the logic in one place instead of scattered across multiple setState calls. It's the same idea as Redux, but built into React.

The three data-fetching hooks

useFileContent(filePath)

Fetches the text content of a file. Returns { content, loading, error }. Has a 150ms delay before showing "Loading..." — this prevents a flash on fast loads. Uses a cancelled flag to ignore stale responses if you click a new file before the first one loads.

useFileMeta(filePath)

Fetches metadata: file size, whether it's an image, whether it's binary, and the extension. This is what the viewer uses to decide which component to render.

useAutoSave(filePath, onDirtyChange)

Manages the save cycle. Returns two functions:

  • bufferChange(content) — call this on every keystroke. It stashes the content in sessionStorage and starts a 2.5s debounce timer
  • getBufferedContent() — retrieves the buffered content (used when reopening a tab with unsaved changes)

When the component unmounts (you close the tab or navigate away), the cleanup function fires a final save if there's unsent buffered content. This prevents data loss.

How the FileTree stays fresh

Look at the useEffect in FileTree.tsx (line 70-87):

const es = new EventSource("/api/watch")
es.onmessage = () => { fetchTree() }

It opens an SSE connection to the server's file watcher. Every time any file changes on disk, the server pushes a message, and the FileTree re-fetches the entire tree. This is why you see new files appear immediately after creating them in the terminal.

The virtualizer (@tanstack/react-virtual) is there for performance: instead of rendering 10,000 DOM nodes for a large project, it only renders the rows currently visible in the scroll viewport. The rest are "virtual" — calculated but not in the DOM.

Hands-on: trace a click yourself

Start Deck with bun dev and open Chrome DevTools (Network tab). Then:

  1. Click a markdown file in the sidebar. Note which API requests fire and in what order.
  2. Click a PNG image. How does the request pattern differ?
  3. Open the same markdown file again from the sidebar. Does it re-fetch from the server?
  4. Edit the markdown and watch the Network tab — when does the save request fire?

Write down what surprised you. Surprises are learning — expected behavior is just confirmation.
