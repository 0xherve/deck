Lesson 1.3

Find and Fix a Real Bug

Now that you can read the code, it's time to change it. This lesson gives you three real bugs to find and fix in Deck. Each one tests a different part of what you learned.

How to debug

Before you touch code, you need a method. Most bugs are found with the same loop:

  1. Reproduce — can you make the bug happen reliably? If not, you don't understand it yet
  2. Narrow — is it a server bug or a client bug? Check the Network tab. A 500 response means server. Correct response but wrong display means client
  3. Hypothesize — form a specific guess: "I think X function returns Y when it should return Z"
  4. Verify — add a console.log (server) or check DevTools (client) to confirm or reject your guess
  5. Fix — change the minimum amount of code. One line is ideal
  6. Check for siblings — does the same mistake exist elsewhere? Grep for the pattern

The most common debugging mistake: changing code before understanding the bug. If your fix is "I tried things until it worked," you haven't debugged — you've just moved the bug somewhere you haven't tested yet.

Bug 1: The git status parser misses renames

Severity: Medium. Renamed files show incorrect status in the sidebar.

How to reproduce:

  1. In a project with git, rename a tracked file: git mv old.txt new.txt
  2. Open Deck and look at the source control panel
  3. The renamed file should show status "R" but the parser doesn't handle it

Where to look:

Open server/routes/git.ts, the /api/git-status handler (around line 37). Look at the status parsing logic. Run git status --porcelain in a terminal after a rename and compare the output format to what the parser expects.

Hint:

Git's porcelain format for renames looks different from other statuses. The git-status documentation describes the full format. Pay attention to how renamed files encode both the old and new path.

What to learn here: Reading specs matters. The git status porcelain format is precisely defined. The current parser was written from memory, not from the spec — and it shows. After fixing this, you'll know the format well enough to never make this mistake again.

Bug 2: The file watcher debounce is too aggressive

Severity: Low, but noticeable. When multiple files change (e.g., saving two files quickly), only the last change event gets through.

How to reproduce:

  1. Start Deck and open the file tree
  2. In a terminal, quickly create two files: touch a.txt && touch b.txt
  3. The file tree may only refresh once instead of showing both files appearing

Where to look:

Open server/routes/files.ts, the /api/watch handler (around line 141). Look at the debounce logic. Each new event clears the previous timer, meaning rapid events collapse into one.

The question:

Is this actually a bug, or is it working as intended? The FileTree re-fetches the entire tree on any event, so one event is enough to show all changes. Think about whether the "fix" is to change the debounce, or to realize the behavior is correct.

What to learn here: Not every behavior that looks wrong is a bug. The debounce collapses events, but since the response is always the full tree, one refresh catches all changes. Sometimes understanding the code means realizing it's already right. However — the SSE only sends the last filename that changed. If a client ever needed to know which files changed (not just "something changed"), this would be a real bug. This is the difference between "works now" and "correct by design."

Bug 3: Closing the active tab can leave you on a dead route

Severity: High. The UI shows an empty editor with no way to navigate back except clicking the sidebar.

How to reproduce:

  1. Open a file in Deck (click it in the sidebar)
  2. Make it the only open tab
  3. Close the tab
  4. The URL still points to /v/filename but there's no tab and possibly no content

Where to look:

Two files are involved:

  • src/stores/tabs.ts — the CLOSE_TAB action. It picks a new active tab, but it doesn't navigate the browser
  • src/components/EditorTabs.tsx — where tabs are rendered. Does closing a tab trigger navigation?

The fix:

When closing the last tab, the app should navigate somewhere — probably / (home). When closing a non-last tab, it should navigate to the new active tab. The reducer already picks the right activeTab; the missing piece is that no code navigates to it.

What to learn here: State and navigation are separate concerns. The reducer correctly updates which tab is active, but React's URL doesn't change by itself — someone has to call navigate(). This is a classic gap in vibecoded apps: the happy path works, but edge cases (closing the last tab) were never tested because the AI didn't think to try it.

After fixing: the checklist

For each bug you fix, verify:

  • Does the fix work for the exact reproduction steps?
  • Did you grep for similar patterns elsewhere? (Are there other places that make the same mistake?)
  • Does the fix break anything else? Test the happy path too
  • Is the fix the minimum change? If you changed more than 5 lines, question whether you're fixing the root cause or adding a workaround
