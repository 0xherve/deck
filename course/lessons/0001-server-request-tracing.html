Lesson 1.1

Read the Server Like a Map

Deck's server is small — about 200 lines across 3 files. By the end of this lesson you'll be able to trace any request from browser to filesystem and back.

The big picture

When you run deck ., here's what happens:

  1. cli.ts parses the command — it reads the directory argument and port option
  2. It calls createServer(rootDir, port) from server/index.ts
  3. That function creates a Hono app — a lightweight HTTP framework, similar to Express but faster and more modern
  4. It mounts three things on the app: security middleware, file routes, and git routes
  5. It starts listening on the port and opens your browser

The key insight: rootDir is the single most important variable in the server. Every route handler receives it when the route factory is created, and every file operation is scoped to it. If you understand how rootDir flows, you understand the server.

The three server files

1. server/index.ts — the wiring

This file does only one thing: it creates the Hono app, mounts the middleware and routes, serves static files, and starts listening. It's 60 lines and has no business logic.

Notice the two serveStatic calls at the bottom. The first tries to serve a real file from dist/client/ (your built React app). The second is a fallback that always serves index.html — this is what makes client-side routing work. Without it, navigating to /v/src/main.tsx directly would 404.

Why two serveStatic calls? This is called "SPA fallback." A single-page app handles its own routing in JavaScript. The server doesn't know about /v/src/main.tsx — it's not a real server route. So when no real file matches, it returns index.html, and React Router takes over from there.

2. server/middleware/security.ts — the guard

Two protections, both simple:

  • Origin guard: Checks the Origin header on every request. If it's not localhost or 127.0.0.1, it returns 403. This stops other websites from making requests to your Deck server. (MDN: Origin header)
  • Path traversal protection: resolveSafePath(rootDir, userPath) resolves the path and checks that the result still starts with rootDir. This stops someone from requesting ../../etc/passwd. (OWASP: Path Traversal)

3. server/routes/files.ts — the core

This is where Deck actually does things. Six endpoints:

GET  /api/tree      → returns the full directory tree as JSON
GET  /api/file      → returns a file's text content
GET  /api/raw       → returns a file as binary (for images)
GET  /api/file-meta → returns size, isImage, isBinary, ext
GET  /api/watch     → SSE stream of filesystem changes
POST /api/save      → writes content to a file

Every endpoint that takes a path uses resolveSafePath to validate it first.

Trace: what happens when you save a file

Follow this path through the code:

  1. The editor detects a change and calls useAutoSave's bufferChange(content)
  2. The content is stashed in sessionStorage (browser memory) immediately
  3. After a 2.5 second debounce, it calls save(content)
  4. save sends POST /api/save with { path, content }
  5. The server's /api/save handler calls resolveSafePath to validate the path
  6. If valid, it calls fs.promises.writeFile — the file is now saved to disk
  7. The fs.watch in /api/watch detects the change and emits an SSE event
  8. The FileTree component receives the event and re-fetches /api/tree

SSE — Server-Sent Events

The /api/watch endpoint uses a pattern called Server-Sent Events. Unlike a normal HTTP response that sends data and closes, SSE keeps the connection open and pushes data to the client whenever something happens.

In Deck, fs.watch watches the project directory. When a file changes, it sends a message through the open SSE connection. The client (in FileTree.tsx) listens with new EventSource("/api/watch") and re-fetches the tree on every message.

The 100ms debounce in the watcher prevents a flood of events when many files change at once (like during a git checkout).

Hands-on: map the endpoints yourself

Open server/routes/files.ts and server/routes/git.ts in your editor. Without looking at this lesson, write down:

  • Every endpoint (method + path)
  • What each one does in one sentence
  • Which ones use resolveSafePath and which don't (and why the ones that don't are safe anyway)

Then open server/middleware/security.ts and answer: could a malicious website running in another tab make requests to your Deck server? Why or why not?
